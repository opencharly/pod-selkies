# 2026.242.1235 — fix: advance layer-python off the bare-name pixi dependency

## Summary

One defect, and the two things required to fix it without breaking CI. **The diff is 4 lines
across 2 files** — `charly.yml` and `.github/workflows/deploy.yml` — and all four are accounted
for below.

**The defect.** This candy pinned `layer-python:v2026.235.2057`, a tag that references the candy
`pixi` by **bare name**. `pixi` became the separate repo `opencharly/layer-pixi` in the candy
cutover, so any consumer resolving that tag fails with `unknown candy "pixi"`. `layer-python` fixed
this itself in `v2026.239.1613`; this repo never picked the fix up.

**Why `charly.yml`'s schema line moves.** `charly box validate` — the gate for this change class —
refuses to run at all until it does:

```
charly: error: command "validate": validation error: …/charly.yml:
        schema 2026.240.1943 is required (found "2026.232.0520"). Run: charly migrate
```

That is charly naming the exact remedy. A candy's declared schema version is consulted only when
charly is invoked *in this repo*, never when a consumer fetches it, so no downstream consumer is
affected.

**Why `.github/workflows/deploy.yml` moves with it.** The migration is precisely what makes CI's
pinned charly too old — the mirror image of the same mismatch, and not hypothetical: the first push
of this branch went red with

```
charly: error: command "validate": validation error: …/charly.yml:
        config schema 2026.240.1943 is newer than this charly supports
```

So the migration and the CI pin are **one atomic change**; landing either alone leaves the repo
broken in one direction or the other. The workflow's charly pin therefore moves
`v2026.238.1242` → `v2026.241.1130`.

### 3. RCA of the warning that the first run emitted

The first run of this gate emitted one warning, and it is charly's own, deliberate, and **not**
dismissible as environmental noise — so here is the actual cause rather than a hand-wave.

`plugin_loader.go:434 warnSkippedFHSPlugins()` fires when the running binary is not at
`/usr/bin`/`/usr/local/bin` **and** `/usr/lib/charly/plugins` holds `.providers` manifests. Its own
comment states the intent: those plugins *"were built against a different charly version (issue
#328)"*, so a dev binary must not load them, and the warning exists to make the skip **visible
instead of silent**. Three measurements:

```
(a) What would have been loaded, and how far apart it is:
    $ /usr/bin/charly version   ->  2026.187.2228
    …against a tree that requires schema 2026.240.1943 — 55 days and a schema epoch apart.
    charly refusing to load them is the CORRECT behaviour; loading them would be the defect.

(b) Is it caused by this PR? No — it fires identically on an untouched clone of main:
    $ git clone --depth 1 …/pod-selkies /tmp/psel-main && cd /tmp/psel-main
    $ charly box validate 2>&1 | grep -c 'dev/worktree build'
    1

(c) Does the skip weaken THIS gate? Provably not. CHARLY_PLUGIN_ONLY=1 is documented in
    plugin_loader.go:454 as "the supported way to resolve AS-IF-UNPACKAGED" — it DROPS the FHS
    path from the search entirely, so nothing is masked. Its output is byte-identical to the
    normal run minus the warning line:
    $ diff <(normal-run | grep -v 'dev/worktree build') <(CHARLY_PLUGIN_ONLY=1 run)
    IDENTICAL
```

So the fix is not suppression: dropping a plugin dir belonging to a different charly build is the
correct resolution mode for a dev binary, the flag is charly's documented seam for it, and the
validation result is proven unchanged by it. The gate in §1 is genuinely at zero warnings.
