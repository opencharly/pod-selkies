# 2026.246.2210 — fix: selkies VAAPI-encode check treats iGPU-without-H264-encode as N/A

## Summary

The `selkies-vaapi-encode` check FAILED on AMD/Intel GPUs that expose no H264
VAAPI encode entrypoint (e.g. the AMD Raphael/Mendocino iGPU, which supports H264
decode but not encode). For a CPU-only box (the openclaw-desktop box is CPU-only
by design — no nvidia/cuda candy), the CPU x264 fallback is the VALID streaming
path, so the FAIL was a false positive that broke the desktop bed's check-live on
GPU-less or iGPU-only hosts.

Fix: the AMD/Intel-no-H264-encode branch now emits `VAAPI-N/A` (PASS) with a note
that the CPU x264 fallback is the valid path, instead of FAIL. The check still
PASSes with `VAAPI-ENCODE-CAPABLE` when H264 encode is present, and still reports
N/A for no-GPU and NVENC paths.

The same false-positive class is fixed in the `selkies-encoder-active` check (the
pixelflux encoder check): an AMD/Intel GPU with CPU fallback now emits
`ENCODER-OK` (CPU x264 is the valid path) instead of FAIL.

The `selkies-frame-not-black` check's `eventually` window is widened from 90s to
300s. **RCA:** the check captures a desktop frame and verifies the luma spread is
above a threshold (the desktop is rendering visible content, not frozen). On a
GPU-less host the selkies desktop takes longer than 90s to render its first visible
frame (the CPU x264 path is slower to start), so the 90s window expired before the
desktop produced a non-uniform frame — a timing false positive, not a rendering
failure (verified: the frame captured after the window has spread=219, well above
the threshold of 24). 300s gives the CPU path time to render.

The candy's own CalVer moves because changed content must ship under a new version.
